## Record each real run

Store a small run record and redacted artifacts under the owning task's evidence directory, with large private transcripts outside Git. Use existing Protocol Verification receipts if a verifier is configured; the Markdown record is a human-readable evidence index, not a new wire format.

Every record must contain:

- User intent, success criteria, contract revision and required properties by shared layer: static/build, component, integration, journey, runtime path, qualitative/domain.
- Actual CLI command or TUI entry action; prerequisites and environment: OS/architecture, terminal/size, repository/base/dirty snapshot, selected grant and restrictions, the model/provider that actually served the run as observed from the harness (PIO never selects or injects one), and authentication class/route without secrets.
- Token usage from the harness's own reports, counted against the owner's per-harness cap in [PLAN](work/standalone-0.1/PLAN.md#owner-amendment-after-m1-acceptance-2026-09-16); missing usage is unknown liability, never zero. Mark usage counted against another provider's cap as a proxy (GLM/Kimi until per-provider caps exist). Harness configuration digests before and after the run where the harness writes durable configuration, with raw snapshots kept outside Git.
- Exact PIO Git commit **and dirty-tree digest if applicable**, build/artifact hash, Protocol pin, adapter version, resolved harness version/binary hash and configuration identity. A source SHA alone is not runtime identity.
- Correlated test-run, caller command/request, execution, invocation/effect/delivery, native session/turn, installation/store incarnation, host slot/process-start generation, controller epoch, workspace lease and completion identities. Use `unavailable` with a reason where the adapter exposes none; do not fabricate IDs.
- Ordered steps; expected visible and durable outcomes; actual observations with timestamps/cursors; artifact paths/digests and exact reproducible commands with exit status. Redact credentials and private task content without hiding capture gaps.
- Real versus simulated components, fault injection points, untested segments, observed property results (`pass`, `fail`, `not_evaluated`, `indeterminate`), limitations and attributed acceptance. Record the negative control and its expected distinguishing failure.

Future command names below are intents, **not existing PIO commands**. Each milestone must replace them with actual runnable commands and input fixtures in its run record. Do not turn a headless API pass into TUI proof or a fake process into real-adapter proof.

## Additional release coverage

The six journeys do not replace component/property tests. Required coverage includes journal failure before dispatch, launch-before-record crash window, stale controller/worker, PID reuse, duplicate/conflicting completion, late old-attempt receipt, revocation, bounded stream loss, budget exhaustion/unresolved liability, dirty/untracked checkpoint coverage, migration failure, retention with active dependencies, export/import and restoring an older store while a host survives. The restore must hold new admission until reconciliation; incarnation alone is insufficient.

For a critical path or recovery test, the negative control must execute and fail the intended property with usable artifacts. A missing executable or crashed runner is not a successful sensitivity test. Repeating a test supplies a sample count, not universal correctness. All absent runtime evidence remains `not_evaluated`; inaccessible or ambiguous observations are `indeterminate`.

Milestone reports name accepted properties and remaining obligations separately. Human acceptance, code merge, install/deploy and a working user journey are distinct facts. Confirmatory product-quality thresholds are frozen after pilot measurements and owner judgment, as specified in the release plan.
