# ADR 003 — Codex app-server adapter behind the durable host

- Status: **proposed builder design**, 2026-09-16, for owner and independent review on [PR #6](https://github.com/Combraton/pio/pull/6). Implementation proceeds offline against it. Items marked **owner gate** are presented with the live-run plan on [issue #5](https://github.com/Combraton/pio/issues/5) and are not exercised live before the owner's go.
- Owner: Claude Code session, standalone PIO M2 builder. Scope: PIO-local adapter and service mode. No Protocol schema change.
- Inputs: [ADR 001](001-standalone-stack.md) and its 2026-09-16 amendment, [ADR 002](002-protocol-journal.md), [M2 task](../work/m2/TASK.md), the [pinned app-server README](https://github.com/openai/codex/blob/e363b08c9175ac1cbe5893615dd2cb9ddf95043b/codex-rs/app-server/README.md), the schemas generated by the qualified binary, the pinned [EXECUTION profile](https://github.com/Combraton/protocol/blob/cbf8e4df9df2ca8a9b50264df6acace6e4c3a0fc/docs/spec/profiles/EXECUTION.md), and the [qualification and offline probe evidence](../work/m2/codex-qualification/README.md).

## Problem

M2 must run the user's installed Codex 0.146.0 through PIO's durable host, preserving its native loop, configuration and permissions, and prove J1, J3, J4 and J5 plus approval deny and allow. The M1 host drives a labeled fake child over a release pipe. The app-server is a JSON-RPC peer that needs a handshake, a thread, a turn, approval responses, interrupts and token accounting. It also writes durable state into the user's Codex home.

## Decisions

### 1. Service mode and qualification

- A separate `pio serve-codex --data-dir DIR --config FILE --socket PATH` mode, with a `pio-codex-service/1` configuration naming the selected executable path and the environment passed to Codex (`PATH`, `HOME`). The M1 fake service and conformance participant are unchanged.
- The selected executable is qualified with `pio-codex` at service start and again before every launch. A launch re-hashes wrapper, Node and native binary; any change re-runs full qualification, including schema identity. An unqualified executable is refused before native work, and discovery reports it as not usable.
- Qualification's Node is the first `node` on the **service's** `PATH`, not the operator's shell. Receipts record which one ran.

### 2. Content bytes for digest-only fields

Protocol v0.1.0 carries the brief (`execution.submit`), steering message (`execution.steer`) and action response (`execution.respond_action`) only as `{digest, media_type}`. The EXECUTION prose mentions "an inline bounded brief", but the frozen schema has no such member, and no content path exists without the Evidence profile.

- **Choice:** an optional PIO extension `pio.combraton.dev/content` on those commands: `{"media_type": …, "text": …}` for UTF-8 or `{"media_type": …, "base64": …}`. Before admission the provider verifies that the SHA-256 of the bytes equals the payload digest and that media types match, then stores the bytes in its content-addressed spool. A mismatch is `invalid_envelope` at `/extensions/pio.combraton.dev~1content`. A missing extension leaves the content unavailable: the brief's execution is refused at admission with `capability_unavailable` naming the content, and no native work starts.
- **Why optional, not in `requires`:** Core defines no negotiation for extension keys. The digest already binds the bytes, because a different text is a different digest and therefore a different command digest. Retransmission and replay stay safe, and replays need no bytes.
- **Limits:** bytes fit inside the 1 MiB frame. The extension is not a Protocol feature. A Protocol issue will ask for a defined content path and point out the prose/schema mismatch.
- **Alternatives rejected:** a non-Protocol upload method on the same socket (outside every profile); a shared file drop (a shared writable store, which is forbidden); implementing Evidence artifacts now (outside M2 scope).

### 3. Host process and native identities

- The durable host keeps M1's fences: journal intent before launch, launch guard, fenced host slot, controller generation, independent `spawn` marker.
- The launched child is the selected executable with `app-server` over stdio, without `env_clear` (Codex needs the user's environment). For the npm install this is a Node wrapper whose child is the native binary. The host records both the wrapper and native process identities (kernel start identity) and verifies the native child's executable path and hash against the qualification record before the handshake.
- **Phase mapping:**
  - `host_claimed` → spawn
  - `parked`: `initialize`/`initialized`, `account/read` (the authentication type only, never email or tokens), configuration snapshot, then `thread/start`; journal the native thread id
  - `released`: commit, then `turn/start`
  - `completed`: `turn/completed`
- The native `thread.id` and `turn.id` are journaled beside the invocation, so recovery can correlate native session and turn with host slot and controller generation.

### 4. Delivery, output, usage and results

- **Delivery:** the `turn/start` response carrying `turn.id` is a correlated native acknowledgment, recorded as `acknowledged` with proof class `provider_ack_id`. `turn/started` corroborates it. Neither proves comprehension. If the host dies after the release commit and before a response, the delivery is `ambiguous` until reconciled; it is never re-sent.
- **Output:** `item/agentMessage/delta`, `item/commandExecution/outputDelta`, `turn/diff/updated` and final `item/completed` records go to the content-addressed spool as JSON lines with offsets. Journal records hold references only.
- **Usage:** `thread/tokenUsage/updated` totals are observed usage against the owner's per-harness cap; they are not a billed amount. A turn with no usage notification records unknown liability, never zero.
- **Results:** `turn/completed` status `completed`, `interrupted` or `failed` becomes the receipt and exit observation, with `codexErrorInfo` preserved. Completion is not verification or acceptance.
- **Network:** `thread/start` can open an upstream connection before any turn (see the probe). PIO never calls it offline.

### 5. Approvals, steering and cancellation

- **Approvals:** `item/commandExecution/requestApproval`, `item/fileChange/requestApproval` and `item/permissions/requestApproval` become Protocol native actions: runtime `requires_action` and a pending `action_id` that survives restart. The host holds the JSON-RPC request id and waits. `execution.respond_action` commits an `execution.action_response` effect; its content bytes (decision JSON) are verified, and the host sends exactly that decision. `serverRequest/resolved` and the item's `item/completed` status (`completed` or `declined`) are the observed outcome.
- **Allowed decisions:** `accept`, `decline` and `cancel` only. `acceptForSession`, execpolicy amendments and network-policy amendments widen standing permissions and are refused as `invalid_envelope`.
- **Other server requests:** `item/tool/requestUserInput`, MCP elicitations, dynamic tool calls and attestation requests are declined or cancelled natively and recorded. PIO does not answer on the user's behalf.
- **Steering:** `turn/steer` with `expectedTurnId`. Its response `{turnId}` is the acknowledgment; behavior stays `not_observed` until attributable output.
- **Cancellation:** `turn/interrupt`. The empty response is only a request acknowledgment; `turn/completed` with `interrupted` is the observed outcome. Background terminals are not claimed stopped.
- **Daemon to host:** control intents (action responses, steer, interrupt) are journal facts the host polls. They are durable before the host acts, and a restarted daemon never re-sends one the host already applied.

### 6. Permissions and configuration

- PIO never selects `danger-full-access`, `externalSandbox`, `thread/shellCommand` or `process/spawn`, and never approves on the user's behalf. After `thread/start`, PIO reads the effective `sandbox` projection and `approvalPolicy`. It refuses before `turn/start` if the sandbox is full or external access or if network access is enabled beyond the grant. The effective model and provider are recorded from the same response.
- **Owner gate:** for M2 fixture tasks PIO proposes requesting `sandbox: "workspace-write"` and `approvalPolicy: "on-request"` explicitly. That is Codex's standard setting for trusted repositories and is required for deny and allow to be observable. If the user's own default is stricter, this request is less strict for that fixture thread. The owner decides before the first live run whether to request these values or to use the user's configuration unmodified.
- Before `thread/start` and after the host exits, PIO snapshots `$CODEX_HOME/config.toml` with `pio-codex` and journals the digests and the diff with fixture-relative labels. Raw snapshots stay in a private evidence directory outside Git. PIO edits nothing.
- The working directory is the execution workspace repository (Protocol `execution.workspaces`): a throwaway fixture repository whose `HEAD` must equal the requested `base` at admission and again at launch.

### 7. Discovery

- `execution.discovery.list` reports the configured installation with separate facts: detected, adapter recognized, version supported (from qualification), reachable, and `authentication`. Authentication stays `unknown` until a launch has observed it through `account/read`, and is then reported with `last_verified`. Discovery never starts an app-server in the user's Codex home merely to probe. Usable requires every fact positive, so a fresh install is truthfully not usable until one live launch has observed authentication.

## Consequences and verification

- **Offline first:** a labeled fake app-server, speaking the pinned JSON-RPC shapes over stdio, drives the host through the handshake, turns, approvals, interrupt, steering, usage, host death and daemon restart in Cargo tests and the public process matrix. The real binary is exercised offline only as in the qualification probe: isolated home, no turn.
- **Live runs:** each live run needs the owner's go on issue #5 and a throwaway fixture repository, and records the evidence fields in [JOURNEYS](../JOURNEYS.md).
- **Existing work:** the M1 fake host, conformance participant, capacity bound and fences are unchanged.
- **Out of scope:** the Claude Code adapter, OpenCode and Hermes adapters, and TUI.
