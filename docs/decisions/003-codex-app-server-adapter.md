# ADR 003 — Codex app-server adapter behind the durable host

- Status: **accepted**, merged with M2 as `16fb2291`. Reviewed independently on [PR #6](https://github.com/Combraton/pio/pull/6); the review at `a376b2a` on 2026-09-17 ("design matches ADR 003") carried the thread-settings decision and four corrections required before the first live run, recorded under [Review 2026-09-17](#review-2026-09-17). Reviews below are the independent reviewer's; a decision marked an owner decision is the owner's.
- Owner: Claude Code session, standalone PIO M2 builder. Scope: PIO-local adapter and service mode. No Protocol schema change.
- Inputs: [ADR 001](001-standalone-stack.md) and its 2026-09-16 amendment, [ADR 002](002-protocol-journal.md), [M2 task](../work/m2/TASK.md), the [pinned app-server README](https://github.com/openai/codex/blob/e363b08c9175ac1cbe5893615dd2cb9ddf95043b/codex-rs/app-server/README.md), the schemas generated by the qualified binary, the pinned [EXECUTION profile](https://github.com/Combraton/protocol/blob/cbf8e4df9df2ca8a9b50264df6acace6e4c3a0fc/docs/spec/profiles/EXECUTION.md), and the [qualification and offline probe evidence](../work/m2/codex-qualification/README.md).

## Problem

M2 must run the user's installed Codex 0.146.0 through PIO's durable host, preserving its native loop, configuration and permissions, and prove J1, J3, J4 and J5 plus approval deny and allow. The M1 host drives a labeled fake child over a release pipe. The app-server is a JSON-RPC peer that needs a handshake, a thread, a turn, approval responses, interrupts and token accounting. It also writes durable state into the user's Codex home.

## Decisions

### 1. Service mode and qualification

- A separate `pio serve-codex --data-dir DIR --config FILE --socket PATH` mode, with a `pio-codex-service/1` configuration naming the selected executable path and the environment passed to Codex (`PATH`, `HOME`). The M1 fake service and conformance participant are unchanged.
- The selected executable is qualified with `pio-codex` at service start and again before every launch. A launch re-hashes wrapper, Node and native binary; any change re-runs full qualification, including schema identity. An unqualified executable is refused before native work, and discovery reports it as not usable.
- Qualification's Node is the first `node` on the **service's** `PATH`, not the operator's shell. Receipts record which one ran.

### 2. Content bytes for digest-only fields

Protocol v0.1.0 carries the brief (`execution.submit`), steering message (`execution.steer`) and action response (`execution.respond_action`) only as `{digest, media_type}`. The EXECUTION prose mentions "an inline bounded brief", but the frozen schema has no such member, and no content path exists without the Evidence profile.

- **Choice:** an optional PIO extension `pio.combraton.dev/content` on those commands: `{"media_type": …, "text": …}` for UTF-8 or `{"media_type": …, "base64": …}`. Before admission the provider verifies that the SHA-256 of the bytes equals the payload digest and that media types match, then stores the bytes in its content-addressed spool. A mismatch is `invalid_envelope` at `/extensions/pio.combraton.dev~1content`. A missing extension leaves the content unavailable: the brief's execution is refused at admission with `capability_unavailable` naming the content, and no native work starts.
- **Why optional, not in `requires`:** Core defines no negotiation for extension keys. The digest already binds the bytes, because a different text is a different digest and therefore a different command digest. Retransmission and replay stay safe, and replays need no bytes.
- **Limits:** bytes fit inside the 1 MiB frame. The extension is not a Protocol feature. A Protocol issue will ask for a defined content path and point out the prose/schema mismatch.
- **Alternatives rejected:** a non-Protocol upload method on the same socket (outside every profile); a shared file drop (a shared writable store, which is forbidden); implementing Evidence artifacts now (outside M2 scope).

### 3. Host process and native identities

- The durable host keeps M1's fences: journal intent before launch, launch guard, fenced host slot, controller generation, independent `spawn` marker.
- The launched child is the selected executable with `app-server` over stdio, started with a **cleared environment plus exactly the allowlisted variables in the service configuration's `codex.env`** (`env_clear` then that map; for the live plan `PATH`, `HOME`, `USER`, `LANG`). Nothing else from the service or host environment is inherited, including credential variables. For the npm install this is a Node wrapper whose child is the native binary. The host records both process identities (kernel start identity), verifies that the launched process's interpreter is the qualified Node, and verifies the native child's executable path and hash against the qualification record before the handshake.
- **Phase mapping:**
  - `host_claimed` → spawn
  - `parked`: `initialize`/`initialized`, `account/read` (the authentication type only, never email or tokens), configuration snapshot, then `thread/start`; journal the native thread id
  - `released`: commit, then `turn/start`
  - `completed`: `turn/completed`
- The native `thread.id` and `turn.id` are journaled beside the invocation, so recovery can correlate native session and turn with host slot and controller generation.

### 4. Delivery, output, usage and results

- **Delivery:** the `turn/start` response carrying `turn.id` is a correlated native acknowledgment, recorded as `acknowledged` with proof class `provider_ack_id`. `turn/started` corroborates it. Neither proves comprehension. If the host dies after the release commit and before a response, the delivery is `ambiguous` until reconciled; it is never re-sent.
- **Output:** `item/agentMessage/delta`, `item/commandExecution/outputDelta`, `turn/diff/updated` and final `item/completed` records go to the content-addressed spool as JSON lines with offsets. Journal records hold references only.
- **Usage:** `thread/tokenUsage/updated` totals are observed usage against the owner's per-harness cap; they are not a billed amount. A turn with no usage notification records unknown liability, never zero.
- **Results:** `turn/completed` status `completed`, `interrupted` or `failed` becomes the receipt and exit observation, with `codexErrorInfo` preserved. Completion is not verification or acceptance.
- **Network:** `thread/start` can open an upstream connection before any turn (see the probe). PIO never calls it offline.

### 5. Approvals, steering and cancellation

- **Approvals:** `item/commandExecution/requestApproval` and `item/fileChange/requestApproval` become Protocol native actions (the permissions request is refused instead; see the re-pin section): runtime `requires_action` and a pending `action_id` that survives restart. The host holds the JSON-RPC request id and waits. `execution.respond_action` commits an `execution.action_response` effect; its content bytes (decision JSON) are verified, and the host sends exactly that decision. `serverRequest/resolved` and the item's `item/completed` status (`completed` or `declined`) are the observed outcome.
- **Allowed decisions:** `accept`, `decline` and `cancel` only. `acceptForSession`, execpolicy amendments and network-policy amendments widen standing permissions and are refused as `invalid_envelope`.
- **Other server requests:** `item/tool/requestUserInput`, MCP elicitations, dynamic tool calls and attestation requests are declined or cancelled natively and recorded. PIO does not answer on the user's behalf.
- **Steering:** `turn/steer` with `expectedTurnId`. Its response `{turnId}` is the acknowledgment; behavior stays `not_observed` until attributable output.
- **Cancellation:** `turn/interrupt`. The empty response is only a request acknowledgment; `turn/completed` with `interrupted` is the observed outcome. Background terminals are not claimed stopped.
- **Daemon to host:** control intents (action responses, steer, interrupt) are journal facts the host polls. They are durable before the host acts, and a restarted daemon never re-sends one the host already applied.

### 6. Permissions and configuration

- PIO never selects `danger-full-access`, `externalSandbox`, `thread/shellCommand` or `process/spawn`, and never approves on the user's behalf. After `thread/start`, PIO reads the effective `sandbox` projection and `approvalPolicy`. It refuses before `turn/start` if the sandbox is full or external access or if network access is enabled beyond the grant. The effective model and provider are recorded from the same response.
- **Owner decision (2026-09-17, option a):** request `sandbox: "workspace-write"` with `approvalPolicy: "on-request"` for R1–R4 and `approvalPolicy: "untrusted"` for R5–R6. Before starting the app-server, the host evaluates the pre-run configuration snapshot and refuses if a requested value is broader than the user's configured default (see the guard below).
- Before `thread/start` and after the host exits, PIO snapshots `$CODEX_HOME/config.toml` with `pio-codex` and journals the digests and the diff with fixture-relative labels. Raw snapshots stay in a private evidence directory outside Git. PIO edits nothing.
- The working directory is the execution workspace repository (Protocol `execution.workspaces`): a throwaway fixture repository whose `HEAD` must equal the requested `base` at admission and again at launch.

### 7. Discovery

- `execution.discovery.list` reports the configured installation with separate facts: detected, adapter recognized, version supported (from qualification), reachable, and `authentication`. Authentication stays `unknown` until a launch has observed it through `account/read`, and is then reported with `last_verified`. Discovery never starts an app-server in the user's Codex home merely to probe. Usable requires every fact positive, so a fresh install is truthfully not usable until one live launch has observed authentication.

## Consequences and verification

- **Offline first:** a labeled fake app-server, speaking the pinned JSON-RPC shapes over stdio, drives the host through the handshake, turns, approvals, interrupt, steering, usage, host death and daemon restart in Cargo tests and the public process matrix. The real binary is exercised offline only as in the qualification probe: isolated home, no turn.
- **Live runs:** each live run needs the owner's go on issue #5 and a throwaway fixture repository, and records the evidence fields in [JOURNEYS](../JOURNEYS.md).
- **Existing work:** the M1 fake host, conformance participant, capacity bound and fences are unchanged.
- **Out of scope:** the Claude Code adapter, OpenCode and Hermes adapters, and TUI.

## Review 2026-09-17

The review of PR #6 at `a376b2a` relayed option (a) for thread settings and required the following before R1. They are implemented in one commit. The version facts in this section are 0.146.0's, as reviewed; the re-pin section below carries what changed at 0.155.1.

- **Thread-settings guard.** From the pre-run `config.toml` snapshot the host reads top-level `sandbox_mode` and `approval_policy`. An absent setting is treated as Codex 0.146.0's default for a trusted project: `workspace-write` and `on-request`, per `ConfigToml::derive_permission_profile` and the approval default in `core/src/config/mod.rs` at `e363b08`. Breadth is ordered `read-only` < `workspace-write` < `danger-full-access` for sandbox, and `untrusted` < `on-request` < `never` for approval, where fewer prompts is broader. A requested value broader than the configured one refuses before the app-server starts (`thread_settings_refused`); the invocation becomes `known_not_released` and delivery `failed_before_delivery`. The following are unresolved and refuse rather than guess: a legacy `profile` key (which 0.146.0 itself rejects), named `default_permissions`, `[permissions…]` tables, and non-string or unknown values. Managed requirements can only narrow further. Every receipt records the configured values and their source from the guard, the requested values, and the effective values reported by `thread/start`.
- **Environment:** the section 3 correction above.
- **Widening decisions:** `acceptForSession` and the execpolicy and network-policy amendment decisions are refused as `invalid_envelope` at `/payload/response`. No effect, control or native answer results. A Cargo test and the offline matrix case `widening_decisions_refused` prove this.
- **Timeouts and deadline stop.** Every live submit carries `timeouts: {delivery: 120, execution_deadline: 600}`. When the execution deadline passes while runtime is not `exited`, PIO appends an `interrupt` control. The host sends a real `turn/interrupt`, and the execution records the request state, the native response and the `turn/completed` status as `deadline_stop`. The host is never killed for a deadline. Protocol §8 leaves runtime, effects and liability as observed; this is the permitted control action. Proven by the offline case `deadline_stop_interrupts`.
- **Node confirmation:** at service start, `/usr/bin/env node` runs with exactly the service `PATH` and reports `process.execPath`. It must be the qualified Node, by canonical path and hash, or startup refuses with `service_node_mismatch`. The record is written to `qualification.json` and carried in the qualification binding. At launch the host also checks that the spawned process's interpreter is that Node.

## Codex re-pin to 0.155.1 and the model exception (owner decision, 2026-09-19)

The owner updated their Codex to **0.155.1** and 0.146.0 is no longer installed. PIO's qualification refused the new binary as `unsupported_version` with exit 3 before any native work, which is what the exact pin is for. The adapter now pins 0.155.1, tag `rust-v0.155.1`, peeled source `be2951ea34f0d295ed0becf97079f92fa5f6950e`, against a [312-file schema identity](../../adapters/codex/0.155.1/schema-identity.json). Measured drift from the previous pin: 312 files, 37 added, none removed, 71 of the original 275 changed canonically. The per-file record and the negative controls are in [codex qualification evidence](../work/m2/codex-qualification/README.md).

Three changes reach this adapter. Each was checked against the labeled fake app-server and the event mapping, not inferred from release notes.

- **Command approvals carry `kind`.** `CommandExecutionRequestApprovalParams` gained an optional `kind`, `command` or `writeStdin`, defaulting to `command` when absent. `writeStdin` is input to a terminal that is already running, not a new command, so a decision that did not record which one it answered would misdescribe what was approved. The host records `approval_kind` on `action_requested` and the adapter keeps it with the action. File-change and permissions approvals have no such field and record `null`. The labeled fake sends the field the pinned version sends, and the offline matrix asserts `command` for the accept case and `writeStdin` for the decline case.
- **`approval_policy = "untrusted"` is no longer accepted in configuration.** 0.155.1 fails to load such a configuration (`UnsupportedUntrustedApprovalPolicyError`) and, as the offline probe shows, the app-server exits 1 before answering `initialize`. The thread-settings guard therefore treats a configured `untrusted` as unresolved and refuses before spawning something that cannot start, instead of reading it as the strictest default. Requesting `approvalPolicy: "untrusted"` for one thread is still accepted, which the probe confirms, so the R5 and R6 plan is unchanged.
- **Permission-grant requests are refused, not surfaced.** Checking the decision sets at the new pin showed something the previous pin had too: `item/permissions/requestApproval` does not take a decision at all. Its response requires a `permissions` profile with a `scope` that defaults to the whole turn, so `accept` would have been an unanswerable shape and, if it had been understood, a grant beyond the settings the thread-settings guard approved. PIO now refuses it natively with `a permission grant would widen the approved thread settings`, surfaces no action, and records the refusal. The offline case `permission_grant_refused` proves no action appears and nothing is answered. `accept`, `decline` and `cancel` remain the only decisions PIO sends, and they remain exactly the non-widening variants of the command and file-change decision enums, which are unchanged at 0.155.1.
- **Path types were renamed and turn-start gained optional fields.** `AbsolutePathBuf` disappears from the approval schemas in favour of `PathUri`, but `cwd` is still a `LegacyAppPathString` on the wire, so nothing PIO reads changed shape. `TurnStartParams` gained `serviceTierForTurn`, `toolOutput` and `turnTrigger`; PIO sends none of them. Comparing property and enum names per definition across the two versions, the only thing PIO could read that disappeared is `Thread.isPinned`, which it does not read.

**The absent-setting default is now measured, not read from source.** With the project already trusted and nothing configured, `thread/start` projects `workspaceWrite` and `on-request`, which is what the guard assumes. The same probe shows an untrusted project defaults to `readOnly` and that requesting `workspace-write` is what writes the trust entry. Every run continues to disclose the trust entry it adds.

### Model: a dated, test-only exception

PIO never selects a model. R1 proved the "harness as configured" route works and also proved the configured model cannot complete a turn at a pinned version: the turn failed upstream with HTTP 400, "The 'gpt-6-astra' model requires a newer version of Codex". That model is also expensive.

The owner's decision of 2026-09-19: run **R1 exactly once** with the configuration untouched and no model passed, under its own 50,000 token stop and with no retry on failure, and pass `gpt-5.6-terra` explicitly for **R2 to R6**. This is recorded here as a dated, test-only exception. The product still never selects a model, and the option is refused outside fixture runs:

- `codex.thread.model` is accepted only when the configuration also carries `test_only_model_exception = "owner-2026-09-19-m2-fixture-runs"`, and that exception is itself refused without a model, so it cannot sit unused in a configuration. An empty model name is refused. A Cargo test covers all four refusals and both accepted shapes.
- Every receipt records the **configured**, **requested** and **effective** model. The configured model comes from the pre-run configuration snapshot, which now reads the top-level `model` key; the effective model is what `thread/start` reports.
- `scripts/codex_live_run.py --run model-list` confirms the model exists for the account with a zero-token `model/list` call before any turn. It starts no turn and reports no usage.

The Codex cap stays 1,000,000 tokens with the stop at 80%.

## Review 3 corrections (2026-09-19)

- **Protocol gap filed.** Reattaching an execution whose delivery is already determined still records `ambiguous` / `dispatch_may_have_begun`, because the frozen `recovery_decision` enum has no value for it. [Protocol #15](https://github.com/Combraton/protocol/issues/15). PIO keeps the inaccurate entry and discloses it rather than widening its local schemas; if #15 resolves the other way, PIO stops emitting a recovery decision once delivery is determined.
- **Budget enforcement is not PIO's yet.** The token stop that bounded the M2 live runs is the live runner's rule in `scripts/codex_live_run.py`, applied through `execution.cancel`. The service and host enforce no budget. Recorded as an open obligation, not a property.
- **`test_only_model_exception` is temporary.** It must be removed or compiled out before release, not merely refused without its dated token.

## L3: a lead on Codex (owner decisions, 2026-09-24 and 2026-09-25)

Four changes reach this adapter for L3, each with a matrix case.

- **The lead tool, on the lead's thread only.** `serve-codex` now accepts the `pio.combraton.dev/lead-tool` extension, under owner authority only; a submit under any grant that carries it is still refused before admission. The host puts the server in that run's own `thread/start` `config.mcp_servers`, the route the M4b probe saw Codex launch, and records `mcp_servers_sent` for every run: the lead's name for the lead, nothing for the others. The spec may name `pre_allowed_tools`, which only this host accepts. It sets `approval_mode = "approve"` for those tools on that server, in that thread's config. By the owner's decision it holds exactly the lead's two tools, is passed per launch, and is never written to the owner's configuration.
- **MCP tool-call approvals are surfaced, not declined.** Codex asks before an MCP tool call that is not marked read-only. This is read from its source at `rust-v0.155.1` and `rust-v0.157.0` and is **not measured**. `codex-rs/core/src/mcp_tool_call.rs` differs between the two tags, but the functions that decide whether to ask, build the request and parse the answer are identical; see the qualification README for exactly which changed. It asks by a form-mode `mcpServer/elicitation/request` whose `_meta.codex_approval_kind` is `mcp_tool_call`. The host surfaces that as an action, with the server, the message and what Codex offered to remember. It answers `accept` as `{"action":"accept","content":{}}`, with no `persist`, which Codex reads as a single approval. `decline` refuses the call, and `cancel` aborts it. `persist: "session"` or `"always"` would remember the approval, the latter in configuration, so PIO never sends it. Any other elicitation (a login, a form asking for data, `browser_auth`, or a tool-call approval in a mode other than `form`, which the schema allows) is declined natively, as before.
- **What PIO declines by itself reaches the stream** (review of L3, CH-2/F1). Until now a request the host answered with an error was recorded in its own events file only, with the reason "no user is attached", which was not the reason. `native_request_declined` now carries the method, the turn and item, and for an MCP elicitation the server, the mode, `_meta.codex_approval_kind` and `codex_request_type`, and the tool's name or title where Codex put one there; for a permission grant, the kinds of permission asked for. Never an argument, a form's content, a URL or a server's message. The reason is the true one. Every run's `execution.exit.observed` carries the list under `pio.combraton.dev/native-declines` (an event that already fires; no new event type), empty when there were none, so "none" and "not carried" differ. The L3 runner fails its pre-allowance row if Codex asked about the lead's tool by this path too, and its desk row on any request PIO declined by itself.
- **An unanswered approval lapses.** Owner decision: "if I don't answer, it lapses". Until now a Codex approval waited for its caller for ever. Now, after the caller's own delivery timeout, the host sends one decline and records `request_denied_by_default`, decided by PIO, never `cancel`. The action carries that deadline and what PIO will send, so the approval walk shows the countdown.
- **What is being approved reaches whoever decides.** The approval payload an action carries (`pio.combraton.dev/approval`) now names it in the harness's own words: the command a command approval names; and for an MCP tool-call approval, the server, Codex's question, and what it offered to remember. Before, a Codex approval said only its method and kind, which no one can decide on.
- **The thread's model and provider are checked from Codex's own answer, before the first turn.** When the service asks for a model (still only under the dated exception), the `thread/start` response's `model` must equal it. When the operator names `expected_model_provider`, the response's `modelProvider` must equal that too. The provider is only ever checked; PIO sends no `modelProvider`. A mismatch records `model_checked` with `matches: false` and ends the run `thread_model_mismatch` with no turn sent.
